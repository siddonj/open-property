# Intent: Phase 2 — Maintenance workflow

Author: Josh (requester); drafted with Claude
Status: Approved
Date: 2026-10-29
Roadmap: [Phase 2 in `intent.md`](../../../../intent.md#phase-2-maintenance-workflow)

## Problem

- Work orders have a status, a vendor, a scheduled date, and a single `cost`,
  but no notion of **due** or **overdue**. Operators can't see what is late.
- The maintenance page filters by status only. You can't narrow it by property
  or unit, and units have no page of their own, so unit-level history is hard
  to find.
- There are no recurring or preventive tasks. Operators re-create routine work
  (filters, inspections, pest control) by hand.
- There is no approval step for expensive work.
- **Bug:** the UI never sets `completed_at`. The maintenance report counts only
  work orders with `completed_at`, so work completed through the UI never
  appears in it.

## Proposed outcome

1. **Due, scheduled, assigned, and overdue views:** the maintenance page and
   dashboard show what is overdue, due soon, unscheduled, and who it is
   assigned to (the vendor).
2. **History by property and unit:** completed and open work orders can be
   filtered by property and unit, from the maintenance page and the property
   page.
3. **Recurring preventive tasks:** templates such as "HVAC filter, every 3
   months, Oakwood Estate". An explicit **Generate due tasks** action creates
   work orders for due occurrences and never creates duplicates.
4. **Approval threshold:** work above an operator-set amount needs explicit
   approval. The approval status is visible, and the work isn't treated as
   approved until someone approves it.
5. **Fix `completed_at`:** set it when a work order is completed and clear it
   when the work order is reopened.

## Affected users and systems

- Operators and staff. The app is still single-user with no auth, so "assigned
  to" means the vendor. Staff assignment waits for Phase 5 user accounts.
- Server: Work orders, Dashboard, Settings, and Reports sections of
  `src/server/index.ts`, plus migration `0002`.
- Client: maintenance page and dialog, property page, dashboard, and settings;
  a new recurring-tasks UI.

## Constraints and non-goals

- **Attachments (photos and documents) are deferred.** The roadmap requires a
  storage design first, and access rules depend on Phase 5 security work.
- No scheduled or cron generation. Recurring work is generated by an explicit
  operator action, as rent charges are.
- No vendor notifications (email/SMS are out of scope).
- No user identity on approvals until Phase 5. Approvals record a timestamp
  only.
- Follow the existing patterns, and use the Phase 1 migration mechanism
  (`migrations/0002_*.sql`).

## Acceptance criteria

- [ ] Operators can see work that is overdue, due soon, scheduled, unscheduled,
      and unassigned, with overdue clearly distinguished from upcoming.
- [ ] Completed and open work orders can be found by property and by unit.
- [ ] Running **Generate due tasks** twice creates no duplicates. Deleting or
      rescheduling a generated work order doesn't cause it to be generated
      again.
- [ ] Work above the threshold shows "Approval required" and can't be marked
      approved without an explicit approval action.
- [ ] Completing a work order sets `completed_at`, and the maintenance report
      reflects it.
- [ ] Existing work-order, dashboard, and report flows still work.
      `pnpm typecheck` and `pnpm build` pass.
